# Plan 01-04 — Real LLM Audit Pipeline

## Goal

Replace the regex-only `analyzeCodeQuality` heuristic with a **real LLM-driven audit**. Each call sends the file to a configured provider's model, gets back a structured report, and the SwarmPanel renders it. The regex pre-check stays as a fast first pass for obvious issues.

## Context

- **What exists today:**
  - `src/lib/agent-swarm/collaboration-protocols.ts` has `analyzeCodeQuality(code, fileName)` — 5 regex rules, ~50 lines, returns `{ score, issues, summary }`. Heuristic only.
  - `src/lib/agent-swarm/agent-specialists.ts` defines `AnjosReviewer.systemPrompt` and the model `claude-sonnet-4-20250514`.
  - `src/lib/ai/api-client.ts` has `chatCompletion()` and `chatCompletionStream()` for 10 providers.
  - `src/components/os/panels/SwarmPanel.tsx` is a placeholder (built in Plan 1.3).
- **What this plan delivers:** the actual LLM audit call, a structured response parser, the SwarmPanel with `Auditar` button and findings list, and a Zustand store for the audit state.
- **Why now:** without a real audit, the Auto-Patch (Plan 1.5) has nothing to act on.

## Tasks

### Task 1.4.1 — Extend `api-client.ts` with `jsonOutput` option

- Add a new optional parameter to `ChatCompletionRequest`:
  ```typescript
  jsonOutput?: boolean;  // hints providers to return parseable JSON
  ```
- In `chatCompletion()` (or a new `chatCompletionJson()`), wire:
  - OpenAI-compatible: `body.response_format = { type: 'json_object' }`.
  - Anthropic: use `tools: [{ name: 'audit_report', input_schema: { ... } }]` and force tool_choice. (If a generic tool-use pathway is too complex, skip and let the prompt instruct "respond only with JSON"; parse with regex fallback.)
  - Google: `body.generationConfig.responseMimeType = 'application/json'`.
- For v1, fall back to a free-form prompt + JSON.parse if `jsonOutput` fails for the provider. Defensive: try `JSON.parse` first; if it throws, attempt to extract a JSON block from the response (regex `\{[\s\S]*\}`); if still nothing, return a single finding of severity `low` with the raw text.

### Task 1.4.2 — Create `src/lib/agent-swarm/llm-audit.ts`

- Types:
  ```typescript
  export type AuditSeverity = 'critical' | 'high' | 'medium' | 'low' | 'info';

  export interface AuditIssue {
    id: string;
    severity: AuditSeverity;
    line?: number;
    title: string;
    description: string;
    suggestion: string;
    fixedCode?: string;  // optional snippet the user can apply
  }

  export interface LLMAuditResult {
    file: string;
    score: number;  // 0-100
    passed: boolean;  // score >= 70 && no criticals
    issues: AuditIssue[];
    securityAnalysis: {
      owaspTop10Checked: boolean;
      sanitizeInputsChecked: boolean;
      authIssuesChecked: boolean;
      vulnerabilitiesFound: number;
    };
    summary: string;
    reviewedBy: string;  // e.g. "AnjosReviewer (claude-sonnet-4-20250514)"
    timestamp: Date;
    durationMs: number;
  }
  ```
- Function: `llmAudit({ code, fileName, providerId, modelId, language }): Promise<LLMAuditResult>`:
  1. Build the system prompt: combine `AnjosReviewer.systemPrompt` with the JSON schema.
  2. Build the user prompt: the file content + language + the request "respond with JSON in the schema".
  3. Call `chatCompletion({ provider, model, messages, jsonOutput: true, temperature: 0.2 })`.
  4. Parse the response into `LLMAuditResult`.
  5. Compute `durationMs`.
  6. Return.
- Error handling: any thrown error becomes a single `AuditIssue` with severity `info` and the error message in `description`.

### Task 1.4.3 — Create `src/lib/agent-swarm/auditStore.ts` (Zustand)

- State:
  ```typescript
  {
    status: 'idle' | 'pre-checking' | 'llm-auditing' | 'done' | 'error',
    currentResult: LLMAuditResult | null,
    history: LLMAuditResult[],  // last 20 audits, most recent first
    preCheckIssues: AuditIssue[],  // from the fast regex pass
    error: string | null,
  }
  ```
- Actions:
  - `runAudit({ code, fileName })` — orchestrates: pre-check via `analyzeCodeQuality` (existing), then LLM audit. Sets status transitions, stores result.
  - `clearCurrent()` — resets to idle.
  - `applyFix(issueId)` — returns the `fixedCode` if present, else null.

### Task 1.4.4 — Enhance `SwarmPanel.tsx` with real audit UI

- Replace the placeholder from Plan 1.3.
- Header: "✨ IA Swarm" + status indicator (idle / auditing with spinner / done / error).
- 7 agent cards in a vertical strip on the side: name, role emoji, model used (from `getActiveProvider()` + a per-agent override), live status (subscribe to `getSwarmEngine().on('agent:status_change', ...)`).
- Main area: `Auditar` button (with file path shown if a file is active in the editor).
- Below the button: the `preCheckIssues` from the fast pass (small cards, low visual weight).
- After the LLM call completes: a list of `AuditIssue` cards, grouped by severity (Critical, High, Medium, Low). Each card has:
  - Severity badge.
  - Title + line number (clickable → jump to line in Monaco).
  - Description + Suggestion.
  - "Aplicar Correção" button (if `fixedCode` is present) → emits an event that Plan 1.5's `PatchApplier` consumes.
- A "Histórico" tab at the bottom showing the last 20 audits.

### Task 1.4.5 — Wire `Auditar` button to the editor

## Out of scope (deferred)

- **Multi-file audit:** the audit is per-file. A workspace-level audit (e.g., "audit everything in `src/`") is a Plan 1.5 or v1.1 feature.
- **Streaming audit output:** for v1, the audit is a single request/response. Streaming (showing tokens as they arrive) is a v1.1 nice-to-have.
- **Custom audit prompts per agent:** the v1 audit uses `AnjosReviewer.systemPrompt` only. Per-agent override is a v1.1.

## Risks

- **LLM hallucinations of `fixedCode`:** the LLM may invent a fix that doesn't compile. Plan 1.5 always shows the diff before applying, so this is mitigated at the UX layer.
- **Provider-specific JSON mode quirks:** the fallback parser handles all the cases but adds complexity. Document the gotchas in `llm-audit.ts` JSDoc.
- **Cost:** a 500-line file with 1 LLM call ≈ $0.01-0.03. Acceptable for v1 but should be tracked. (Phase 3's audit log will surface this.)
